# FTS5 bm25 probe: what SQLite actually computes

Date: 2026-09-01. Task: P2 (Python search port). Probe promoted to
`python/store/tests/test_fts5_semantics.py`, which re-runs every one of these
assertions on every test run.

## Why this exists

The P2 brief and `docs/python-port/digests/store-vector-search.md` section B.5
described FTS5's ranking three ways that real FTS5 contradicts. The port was
about to be written against the description instead of against the thing, so the
thing was run first: a hand-built FTS5 table in the same layout the sqlite facet
builds (external content, `tokenize='unicode61'`, `bm25()` with inline weights),
scored against candidate formulas.

Every finding below is asserted in both directions. The accepted formula
reproduces FTS5's score, and the rejected alternative is shown to differ. A
probe whose conclusion cannot fail is not evidence.

## Findings

**1. Length normalization is over the whole document, not per column.** FTS5's
`D` is the row's total token count across every column, which is what the
existing TypeScript in-memory reference already used. Two documents, each with
the hit in one column and a 40-token filler in the other, columns unweighted:

| formula | scores |
| --- | --- |
| real FTS5 | `l 0.5315189022113783`, `s 0.5315189022113783` |
| whole document | `l 0.5315189022113782`, `s 0.5315189022113782` |
| per column (rejected) | `l 1.8146216166281168`, `s 1.8146216166281168` |

Whole-document normalization agrees to within one unit in the last place. Per
column is off by a factor of 3.4.

**2. The idf floor is `1e-6`, not zero.** The TypeScript memory store dropped a
term whose idf was non-positive. FTS5 floors it at `1e-6` and keeps it, so a term
carried by every document still ranks by frequency instead of collapsing to the
id tie-break. Three documents holding the term once, three times and twice:

| formula | order and scores |
| --- | --- |
| real FTS5 | `b 1.4193548387096774e-06`, `c 1.375e-06`, `a 1.2571428571428573e-06` |
| floor `1e-6` | `b 1.4193548387096774e-06`, `c 1.375e-06`, `a 1.2571428571428571e-06` |
| floor zero (rejected) | `a 0.0`, `b 0.0`, `c 0.0` |

The rejected variant changes the returned order, not only the scores.

**3. Duplicate query phrases are counted once per occurrence.** `bm25()` sums
over MATCH phrases, so `"fox" OR "fox"` scores exactly double `"fox"`:

| query | scores |
| --- | --- |
| `"fox"` | `a 1.4170031313519234`, `b 0.9615378391316625` |
| `"fox" OR "fox"` | `a 2.8340062627038467`, `b 1.923075678263325` |

The digest's claim that sqlite counts a repeated term once is wrong.
Deduplicating is observable in ranking, not merely in scale: on a corpus of
`a: "fox cat cat"` and `b: "cat fox fox"`, the query `fox cat` returns `a, b`
while `fox fox cat` returns `b, a`.

**4. A zero field weight does not unmatch a document.** MATCH runs before any
weight is applied, so the document comes back scoring exactly zero:
`z2 1.2237754316221157`, `z1 0.0`. This is the one premise in the brief that
held, and the TypeScript memory store was the side that needed fixing.

## What was done with it

The Python in-memory reference implements all four rules, and
`python/store/tests/test_search.py` compares it against the Python sqlite facet
on 27 constructed corpora, asserting ids, scores and meta. Falsification, each
mutant reverted after:

| mutation of the Python memory scorer | parity cases turned red |
| --- | --- |
| idf floor changed to 0 | 5 |
| query tokens deduplicated | 2 |
| zero-weighted hit unmatches | 3 |
| per-column length normalization | 6 |

T2 reached the same four conclusions independently against FTS5 and landed them
in `packages/store/src/search/memory.ts`, so the two languages now target the
same behavior from two separate probes rather than from one shared assumption.

The digest's section B.5 and B.4 statements about per-column normalization and
duplicate-token handling are superseded by this record.
