## Coordinator checks

**F1: accept the missing cancellation field and versioned-read shape. Correct the suggested claim-version fix.** The draft already makes a claim token stable across checkpoints and requires internal writes against the current record version. A worker does not need to carry a changing KV version. Specify that the jobs implementation reads and checks the fresh record internally. Expose versions through job reads for administrative operations such as `resolveBlocked`. Define a durable cancellation-request field, its generation scope, and how recovery preserves it. [Draft contract](../proposals/mirk-storage-and-jobs-specifications.md) at line 345, [version conditions](https://github.com/nightwork-dev/mirk/blob/e746b39269b85e905611377391f94601d20a0e9c/packages/store/src/atomic.ts#L91).

**F2: retain the numerical proof; reject a corpus exception and unproved tie-only refinement.** The corpus explicitly checks result membership where float32 rounding can matter. GLM did not inspect or run the selected sqlite-vec implementation, so its statement about that implementation's arithmetic is not verified. Rescoring only native boundary ties does not, by itself, prove that other rounding errors cannot change membership. A per-row host callback is also not an acceptable native implementation. The feature remains pending until a strategy satisfies the full contract without the forbidden host scan. [Existing cutoff scenario](https://github.com/nightwork-dev/mirk/blob/e746b39269b85e905611377391f94601d20a0e9c/packages/store/scripts/scenarios/vector.ts#L638).

**F3: accept explicit participant wiring and the short-work rule.** Current `toAsync` and `toAsyncLog` do not have transaction admission hooks. The factory must bind the supplied stores to one domain and provide synchronous ownership checks for their methods. Keep callbacks limited to short storage work. The lock is per transaction domain, not process-wide as the review states. [Async bridge](https://github.com/nightwork-dev/mirk/blob/e746b39269b85e905611377391f94601d20a0e9c/packages/store/src/to-async.ts#L34), [log bridge](https://github.com/nightwork-dev/mirk/blob/e746b39269b85e905611377391f94601d20a0e9c/packages/store/src/log/to-async-log.ts#L4), [transaction contract](https://github.com/nightwork-dev/mirk/blob/e746b39269b85e905611377391f94601d20a0e9c/packages/store/src/transaction-types.ts#L11).

**F4: accept a concrete lifecycle owner and require the consumer mapping.** The Mirk jobs record can own dispatch lifecycle state, with the asset API deriving its status. Asset-specific fields remain in the application. They do not all need jobs columns or deletion. The draft must name that mapping and exercise asset reads after recovery, instead of leaving two writable lifecycle authorities. See the additional consumer finding below.

**F5: accept the explicit semantic delta.** The current acquisition loop attempts ownership before checking its deadline. The draft intentionally reverses that boundary rule and replaces `now` with `clock`. The inspected owned callers include `@mirk/statements` and coordination tests. A scoped search of Mirk, canonical Gonk Extensions, and Foreclose found no direct Gonk or Foreclose caller of `createSqliteCoordinator` or `SqliteCoordinator`; GLM's Gonk-consumer suggestion remains unverified. [Current acquisition loop](https://github.com/nightwork-dev/mirk/blob/e746b39269b85e905611377391f94601d20a0e9c/packages/store/src/coordination.ts#L314), [statements consumer](https://github.com/nightwork-dev/mirk/blob/e746b39269b85e905611377391f94601d20a0e9c/packages/statements/src/sqlite.ts#L118).

**F6: reject the suggested reduction of Python scope.** The draft explicitly proposes every new portable contract in both languages. The absence of today's Python coordination module establishes implementation work, not a reason to replace the future contract with passive table preservation. Make the Python coordinator deliverable and mixed-language acquisition tests explicit. [Draft scope](../proposals/mirk-storage-and-jobs-specifications.md) at line 20.

## Additional source findings

**Lease expiry is not an atomic mutation condition today.** `StoreCondition` supports missing, present, and version checks. An external time check followed by an asynchronously queued mutation can cross expiry without any version change. The jobs spec promises more than that sequence establishes. Require a shared writer transaction for the read, clock decision, and transition, and define the lease decision point after writer admission. Alternatively, specify a new backend capability deliberately. An atomic-capable `AsyncStore` alone does not settle this requirement. [Condition union](https://github.com/nightwork-dev/mirk/blob/e746b39269b85e905611377391f94601d20a0e9c/packages/store/src/atomic.ts#L91), [draft requirement](../proposals/mirk-storage-and-jobs-specifications.md) at line 345.

**The existing asset backend interface does not carry a worker claim through completion.** `claimForProcessing` returns `AssetMetadata`, while subsequent updates take only an ID and update data. A stale worker cannot be distinguished from a successor by those arguments alone. The integration must carry the original claim into every worker transition. Keep the user journey, but permit the necessary internal interface change. Also define how the proposed blocked state appears through the existing asset status schema, which currently has no blocked value. Backend interface: `ai/llm-service/packages/server/asset/asset/src/types/index.ts:208` (private source), asset statuses: `ai/llm-service/packages/server/asset/asset/src/types/index.ts:6` (private source), worker update sites: `ai/llm-service/packages/server/asset/asset/src/service/asset-service.ts:727` (private source).

**Logical command replay needs an explicit design.** Existing atomic receipts compare a digest of the exact mutation request. Reconstructing an enqueue or claim with a new timestamp, owner token, or expected version changes that request. Specify how a logical retry reproduces its original request or resolves a durable command outcome before generating new fields. Do not equate exact atomic-request replay with arbitrary jobs-command replay. [Receipt check](https://github.com/nightwork-dev/mirk/blob/e746b39269b85e905611377391f94601d20a0e9c/packages/store/src/backends/memory.ts#L235), [request digest construction](https://github.com/nightwork-dev/mirk/blob/e746b39269b85e905611377391f94601d20a0e9c/packages/store/src/atomic.ts#L607).

The review does not establish compatibility of the new vector contract with Qdrant, libSQL, or SurrealDB. Those implementations were outside GLM's inspected source scope. No application, migration, native vector path, or cross-process race was run.

## Review: Mirk storage and jobs specifications (draft, 5 Nov 2026)

### 1. Verdict and scope

**Adopt with five corrections.** This is a specification review at Mirk `c481505` — source inspection only, no runtime verification, no implementation. The draft's "Seen" claims are accurate everywhere I checked them; the eight contracts are coherent with each other and with the current implementation; and §8 correctly resolves the heritage tension (storage in Mirk, execution stays with Gonk, no parallel lifecycle). The criteria are the right ones. Nothing here is unnecessary: each of the eight maps to one of David's eight requests, and the draft declines the framings the earlier evaluation rejected (no queue runtime, no second delivery contract, Fabric excluded). The findings below are implementer-blocking decisions and unstated deltas, not architecture objections.

### 2. Findings (ordered by importance)

**F1 — §8: the claim-transition API leaves the version channel and pending-cancellation representation undefined (draft lines 327–345).** Line 345 requires every mutation to "conditionally write against the current record version," but no operation signature returns the post-mutation version, while `resolveBlocked(id, expectedVersion)` and `removeTerminal(id, expectedVersion)` take a caller-supplied version. Concrete failure: a healthy worker claims (v3), checkpoints (v4), then completes with a handle still carrying v3 → spurious conflict. Related: `requestCancel` (line 333) "records cancellation against the active attempt," but the six-state list (line 323) has no cancel-pending representation, so it is unspecified where that flag lives and how eligibility and `recoverExpired` observe it. Minimal correction: state that every claim-scoped transition returns the fresh record version (or the claim handle carries it opaquely), and define pending cancellation as a field observed by both the eligibility check and expiry recovery. Seen: signatures and contract text; the underlying conditional mutation is expressible today (seen: `mutateAtomically` conditions in `backends/memory.ts`; `decideAtomic` in `sqlite-core.ts:1045`). The rest of the claim/fencing design — stable token checked together with generation, state, expiry; receipts idempotent but not provider-once — is sound and matches the store's receipt machinery.

**F2 — §2: name the sanctioned outcome for the float32 boundary before delivery step 4, not just the open check (draft lines 105–113, 377).** The draft honestly discloses this (line 107: native scalar computation is "a candidate implementation, not a demonstrated solution"), so this is a decision gap, not a hidden defect. Seen: `vector/float32-score-cutoff` (`scripts/scenarios/vector.ts:630–647`) requires the float64-distinct pair `[1, 0.0001, 0]` vs `[1, 0, 0]` to decide topK membership and an inclusive `minScore: 1` floor; sqlite-vec's f32 distance computes in float32, which collapses that gap, so line 105's requirement ("a score tolerance does not permit returning the wrong document") may be unsatisfiable on the proposed path. An implementer who demonstrates the collapse has no defined next move. Minimal correction: state the rule now — either a defined refinement pass whose correctness does not rest on a fixed oversample factor (e.g., host re-scores only candidates whose float32 score ties the boundary score), or an explicit corpus carve-out scoped to this engine documenting float32-equality behavior. Also state explicitly that a per-row JS callback is not "native," since it recreates the host scan line 111 forbids.

**F3 — §6: state the sync-participation mechanism and the short-work rule for memory (draft lines 253–266).** The sketch's synchronous `kv.put`/`log.append` inside an awaited transaction requires the memory stores to read the coordinator's async context synchronously and reject foreign-context calls. That pattern exists in Python's log (`_check_caller`/`LogTransactionError`, `python/.../log.py:143` — seen) but neither TS memory store has it today; `InMemoryLogStore.transaction` is a plain length-restore (`log/memory.ts:57`), and `toAsync` is a pure promise wrapper with no coordinator hook (`to-async.ts`). "Extends the admission path" (line 258) is the right intent; the implementer decision — factory wiring store instances to one coordinator/domain — should be stated. Second, "unrelated async calls queue until it ends" (line 257) makes the store a process-wide lock for the transaction's duration; the SQLite engine documents "short, database-only async work" (`sqlite-core.ts:600–604`) and the memory contract drops that rule — a worker awaiting provider I/O inside a memory transaction deadlocks against the queued calls. Restate the short-work rule. The checkpoint list itself is complete and correct (seen: KV, collections, versions, receipts are exactly the private state of `backends/memory.ts`), and deleting the append-length-only rollback path follows delete-before-add.

**F4 — §8: decide the lifecycle owner instead of requiring the integrator to (draft lines 360–362).** The draft correctly absorbs the heritage objection — Gonk keeps execution (line 360), the module opens no database, and replacing Gonk's corresponding persistence prevents a parallel codepath. But "the integration must establish one owner for each persisted state transition" (line 362) defers the actual decision. Concrete failure: the llm-service asset record's lifecycle state and the jobs record's state are both written at dispatch; a crash between them leaves disagreement, and the acceptance journey passes if the fixture always writes both in one transaction while production recovery reads only the jobs record. Minimal correction: name Mirk's jobs record the sole transition authority, make application state derived and updated in the same storage-domain transaction (the mechanism line 358 already provides), and add an acceptance step reading the asset after the killed-dispatcher recovery. Seen: `IAssetMetadataBackend` at the cited location carries priority, queue, and cancellation operations as claimed.

**F5 — §7: two behavior changes from current code are presented as refactors (draft lines 285–305).** Seen: current `#acquire` makes one more acquisition attempt at/after the deadline before throwing (`coordination.ts:300–318` loop order: try → deadline → sleep); line 300 forbids that final attempt. Deliberate and defensible for determinism, but it changes `runExclusive` at the boundary — a lease freeable exactly at the deadline is no longer taken. The `clock` option also breaks `SqliteCoordinatorOptions`; the callers are not enumerated (Gonk is a consumer — inferred, not verified). Minimal correction: mark both as intended semantic changes and list the owned callers updated in the same release. The frozen-clock diagnosis itself is accurate (seen: lease math uses injected `now`, waits/renewal use real `setTimeout`/`setInterval`).

**F6 — §3: coordination lease tables are specified for "both languages" with no Python implementer (draft lines 124, 144).** Seen: coordination exists only in TypeScript (no coordination module under `python/store/src/mirk/store/`). Documenting lease tables in the Python README is reasonable for the file guarantee, but say that Python reads and preserves those tables without a coordinator port, so the doc does not imply a parity contract that nothing tests.
